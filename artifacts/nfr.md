# Нефункциональные требования (NFR)

> **Проект:** Trading Agent — AI-советник для интрадей-трейдинга
> **Дата:** 14 марта 2026
> **Домен:** Финтех (интрадей-трейдинг, MOEX)

---

## 1. Производительность (Performance Efficiency)

### 1.1 Профиль нагрузки
- **DAU (Daily Active Users):**
  - MVP: 1-5 пользователей
  - Через 6 месяцев: до 100 пользователей
- **Одновременные сессии (пик):** ~20-30 (торговая сессия MOEX 10:00-18:50 МСК)
- **Мониторинг тикеров на пользователя:** до 5 (MVP), до 7-10 (v2.0)

### 1.2 Время отклика (Latency)
- **Генерация рекомендации по тикеру:**
  - 🎯 Цель: < 15 секунд
  - MVP: < 60 секунд (допустимо)
- **Push-уведомления (при резком изменении sentiment):** < 60 секунд
- **Загрузка мини-приложения (графики):** < 3 секунд [💡 Предложение: стандарт для мобильного web]

### 1.3 Пропускная способность
- **MVP:** ~5-25 запросов анализа в минуту (5 пользователей × 5 тикеров)
- **Через 6 мес:** ~500 запросов в минуту (100 пользователей × 5 тикеров)
- **Sentiment pipeline:** обработка новостных/соцсети потоков в near-real-time (задержка < 60 секунд)

## 2. Надёжность (Reliability)

### 2.1 Доступность (Availability)
- **MVP SLA:** 95% (до 18 дней простоя в год)
  - *Перевод:* pet-проект, при падении перезапуск вручную
- **Целевой SLA (при выходе на рынок):** 99% (до 3.5 дней в год)
  - *Перевод:* простой в пару часов допустим, трейдер торгует руками
- **Критичное время:** торговая сессия MOEX (10:00-18:50 МСК, пн-пт). Простой вне сессии некритичен

### 2.2 Целостность данных (RPO)
- **Критичные данные (нельзя потерять):**
  - Веса и параметры обученной модели
  - Настройки стратегии пользователя
- **Восстановимые данные:**
  - Журнал сигналов и рекомендаций (можно пересчитать)
  - Кэш sentiment-данных
- **RPO:** < 24 часов для критичных данных [💡 Предложение: ежедневный бэкап модели и конфигов]

### 2.3 Скорость восстановления (RTO)
- **MVP:** < 2 часов (ручной перезапуск на домашнем сервере)
- **Целевой:** < 30 минут (автоматический рестарт)

## 4. Масштабируемость (Scalability)

### 4.1 Ожидаемый рост
- **Сейчас (MVP):** 1-5 пользователей, 3-5 тикеров, ~100 MB данных
- **Через 6 месяцев:** до 100 пользователей, 15-20 тикеров в пуле, ~10 GB данных
- **Через 1 год:** до 500-1000 пользователей (при успешном выходе на рынок)

### 4.2 Требования к масштабированию
- **MVP:** вертикальное (домашний сервер)
- **Production:** горизонтальное масштабирование — опционально, при > 100 пользователей
- **Потолок MVP-архитектуры:** 100 пользователей × 5 тикеров = 500 активных мониторингов

### 4.3 Узкие места для масштабирования
- Скорость inference модели при увеличении числа пользователей
- Rate limits T-Invest API и источников данных (парсинг)
- Вычислительные ресурсы домашнего сервера для NLP (sentiment)

## Сводка аналитика

### Главные вызовы
1. **Inference latency vs количество пользователей** — при 100 пользователях × 5 тикеров модель должна обрабатывать ~500 запросов. На домашнем сервере с бесплатным Mistral API это может стать узким местом
2. **Rate limits внешних API** — T-Invest API, Mistral API и парсинг Т-Пульса имеют ограничения. Нужна стратегия кэширования и очередей
3. **Парсинг Т-Пульса** — скрапинг может быть заблокирован. Нужен fallback на альтернативные источники sentiment
4. **Юридический дисклеймер** — без лицензии ЦБ формулировки рекомендаций должны быть аккуратными («информация для анализа», а не «рекомендация купить»)

### Серые зоны
- **Точный rate limit T-Invest API** для gRPC streaming — требует тестирования
- **Ресурсы домашнего сервера** — неизвестны точные характеристики (CPU, GPU, RAM). Влияет на feasibility inference < 15 секунд
- **Стратегия переобучения модели** — как часто, автоматически или вручную? Требует уточнения на этапе архитектуры
- **Формат хранения токена T-Invest API при мультипользовательском режиме** — каждый пользователь подключает свой токен? Или один общий?

### Рекомендации
1. **Провести нагрузочное тестирование** на домашнем сервере — измерить реальное время inference для модели
2. **Заложить очередь задач** (task queue) в архитектуру — для буферизации запросов при пиковой нагрузке
3. **Кэшировать sentiment** — не считать заново для каждого пользователя, если тикер тот же
4. **Юридическая консультация** — уточнить формулировки, чтобы не попасть под регулирование ЦБ
5. **Определить характеристики сервера** — перед началом разработки, чтобы архитектор мог заложить реалистичные ограничения
