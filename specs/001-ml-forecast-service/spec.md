## Context & Motivation

Finzooka — AI-советник для интрадей-трейдеров MOEX. Сейчас прогнозная логика существует
только в исследовательском ноутбуке `ML_ТМБ.ipynb`: кастомная реализация ARMAExo
(AR + MA + экзогенные признаки) на дневных (D1) данных и побочный классификатор
«голубая фишка / не голубая фишка». Ноутбук непригоден для продуктива:

- **Нет внятной валидации** — обучение и проверка идут по одним и тем же историям,
  отсюда `R² = -1.15` на GAZP_D1 (хуже baseline’а, предсказывающего среднее).
- **Нет walk-forward** — риск look-ahead утечки (экзогенные признаки считаются
  по полной истории до split’а).
- **Нет мультитикерной проверки** — модель валидирована только на одном инструменте.
- **Нет сервисного контура** — вызов, версионирование, логирование inference,
  регистрация метрик отсутствуют.
- **Нет соответствия конституции проекта** — принципы I (Explainability),
  III (Multi-Factor), V (Model Integrity) по ноутбуку не выполняются.

Данные для обучения уже лежат в `archive/` — 249 тикеров MOEX, OHLCV за период
1999-06 … 2024-08, 9 таймфреймов (MN1 / W1 / D1 / H4 / H1 / M30 / M15 / M10 / M5),
формат CSV с колонками `datetime,open,high,low,close,volume`.

Цель фичи — **выделить математическую модель прогноза в отдельный
gRPC-микросервис**, вытащить лучшее из ноутбука, устранить его дефекты,
довести до состояния, пригодного для использования backend’ом Finzooka
при генерации торговых сигналов.

**Scope**: этот микросервис покрывает ровно контейнер `ML Engine` из
[c4-architecture.md](../../artifacts/c4-architecture.md) — прогнозирование
цены, расчёт уровней SL/TP, технический анализ, классификатор ликвидности.
Контейнер `Sentiment Pipeline` остаётся отдельным сервисом; sentiment-агрегаты
читаются этим сервисом из общего Redis (контракт уже зафиксирован в C4
связях `sentiment → cache → ml_engine`).

## Clarifications

### Session 2026-04-19

- Q: Какой интеграционный контур выбираем — модуль, HTTP, gRPC, Celery? → A: gRPC-микросервис (Option C). Scope = контейнер `ML Engine` из C4; sentiment остаётся отдельным сервисом, агрегаты читаются через общий Redis.
- Q: Какой класс моделей допускаем в scope? → A: ARMAExo из ноутбука — primary candidate с доработками (walk-forward, anti look-ahead, поиск гиперпараметров); если после доработок не проходит SC-001, переключаемся на gradient boosting (LightGBM/XGBoost). ARMAExo в любом случае сохраняется как один из baseline’ов в бэктесте.
- Q: Какой workflow продвижения новой версии модели? → A: Shadow + ручной promote (Option B). Новая обученная версия пишет предсказания в shadow-журнал параллельно с production-версией минимум N дней, не возвращается пользователям; админ сравнивает метрики на свежих данных и нажимает «promote» в admin-панели. N по умолчанию = 5 торговых сессий (≈1 неделя), конфигурируется.
- Q: Источник данных для live inference и пороги свежести? → A: Live-бары и sentiment-агрегаты читаются из Redis (поставщики — отдельные сервисы `Data Collector` и `Sentiment Pipeline` из C4). Пороги свежести: OHLCV — не старше одной длительности запрошенного таймфрейма (для M15 ≤ 15 мин, для H1 ≤ 60 мин и т.д.); sentiment — не старше 60 мин. Если OHLCV устарел — запрос отклоняется с `stale_ohlcv`; если sentiment устарел — fallback на OHLCV-only с пометкой в `factors[]` (FR-014). Пороги вынесены в конфиг.
- Q: Частота автоматического переобучения? → A: Автоматическое расписание — раз в неделю (воскресенье ночью, вне торговой сессии MOEX), половина порога `model_stale = 14 дней`; плюс кнопка «train now» в admin-панели для ручного запуска поверх расписания (Option B).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Получить прогноз цены по тикеру (Priority: P1)

Backend API (оркестратор сигналов) отправляет ML-сервису запрос «дай прогноз по
тикеру SBER на горизонт H ближайших баров таймфрейма M15». Сервис возвращает
ожидаемую траекторию цены, верхнюю/нижнюю границы доверительного интервала,
набор `factors` (какие входные признаки сильнее всего повлияли на результат) и
текущую метрику качества модели на момент генерации (`mape_at_generation`).

**Why this priority**: без этой операции сигналы не существуют. P1 — блокирует
EPIC-003 (генерация торгового сигнала).

**Independent Test**: полностью тестируется вызовом `forecast(ticker, timeframe, horizon)`
на сохранённом историческом срезе данных из `archive/`: результат содержит все
обязательные поля, MAPE на holdout’е не хуже зафиксированного SLA, объяснение
содержит минимум 3 фактора.

**Acceptance Scenarios**:

1. **Given** тикер SBER с ≥1 года истории на таймфрейме M15, **When** backend
   запрашивает прогноз на горизонт 4 бара, **Then** сервис возвращает
   траекторию длины 4, доверительные границы, `factors[]` с оценкой
   вклада каждого признака, `mape_at_generation` и `model_version`.
2. **Given** тикер, у которого менее 500 наблюдений на запрошенном таймфрейме,
   **When** backend запрашивает прогноз, **Then** сервис отвечает явным отказом
   `insufficient_history` без попытки выдать непроверяемое число.
3. **Given** запрос на горизонт, превышающий максимальный обученный (например,
   20 баров при обученном 14), **When** backend шлёт запрос, **Then** сервис
   отказывает с кодом `horizon_out_of_range` и указывает допустимый максимум.
4. **Given** источник экзогенного признака (sentiment) недоступен, **When**
   поступает запрос, **Then** сервис переключается на fallback-режим без
   sentiment и явно помечает в `factors[]` сниженную уверенность.

---

### User Story 2 — Обучить/переобучить модель по тикеру и сохранить версию (Priority: P1)

Администратор (разработчик) через admin-панель или CLI запускает обучение модели
на выбранном тикере и таймфрейме с использованием данных `archive/`. Пайплайн
делает walk-forward валидацию, сравнивает метрики новой версии с предыдущей,
сохраняет артефакт (веса + метаданные) и метрики в журнал.

**Why this priority**: без перетренировки модель деградирует; принцип V
(Model Integrity) требует before/after сравнения метрик. P1 — второй
критический сценарий.

**Independent Test**: запуск `train(ticker, timeframe)` на фиксированном CSV,
проверка, что артефакт сохранён, метрики посчитаны по walk-forward схеме
(минимум 5 фолдов), отчёт «old vs new» сформирован.

**Acceptance Scenarios**:

1. **Given** CSV `archive/M15/SBER_M15.csv`, **When** админ запускает обучение,
   **Then** система выполняет walk-forward валидацию минимум на 5 фолдах и
   публикует метрики (MAPE, RMSE, directional accuracy) per-fold и aggregate.
2. **Given** завершённое обучение, **When** новая модель сохраняется, **Then**
   в реестре фиксируется уникальный `model_version`, таймфрейм, тикер, дата,
   метрики, и формируется сравнение с предыдущей актуальной версией.
3. **Given** новая версия обучена и метрики walk-forward валидации не хуже
   минимальных порогов, **When** завершается обучение, **Then** версия
   помечается `shadow`, помещается в shadow-журнал и параллельно
   с production-моделью пишет предсказания для каждого входящего запроса
   (не возвращает пользователям); через настроенный период (default —
   5 торговых сессий) админ получает отчёт сравнения и может
   продвинуть версию в production одной кнопкой.
4. **Given** метрика MAPE новой версии хуже действующей на ≥ настроенный
   порог, **When** завершается обучение, **Then** новая версия помечается
   `do_not_promote`, в shadow-журнал не попадает, требуется ручное
   решение (отбросить или принудительно отправить в shadow).

---

### User Story 3 — Бэктест модели на исторических данных (Priority: P2)

Админ запускает бэктест текущей продуктовой модели на исторических 6+ месяцах
(из `archive/`) для проверки того, что win rate и MAPE соответствуют заявленным
SLA до релиза.

**Why this priority**: принцип V + Development Workflow требуют бэктеста перед
каждым релизом. Не блокирует первый рабочий прогноз, поэтому P2.

**Independent Test**: `backtest(ticker, timeframe, period)` возвращает таблицу
сигналов vs факт и агрегированные метрики, пригодные для публикации в
admin-панель.

**Acceptance Scenarios**:

1. **Given** модель и тикер, **When** админ запускает бэктест на последних
   6 месяцах, **Then** сервис возвращает массив «сигнал → факт» и сводку:
   MAPE, RMSE, directional accuracy, win rate (% прибыльных рекомендаций).
2. **Given** бэктест завершён, **When** админ смотрит отчёт, **Then**
   отображается сравнение с двумя baseline’ами: `naive` (цена закрытия
   предыдущего бара) и `ohlcv_only` (только OHLCV без экзогенных).

---

### User Story 4 — Наблюдаемость inference в проде (Priority: P2)

Для каждого вызова прогноза сервис фиксирует длительность inference,
использованные источники, текущую MAPE модели, идентификатор версии. Админ
видит агрегаты в admin-панели, получает алерт при деградации.

**Why this priority**: конституция V делает это обязательным, но первый запрос
возможен и без полной телеметрии. P2.

**Independent Test**: 100 синтетических вызовов прогноза; админ-панель/лог
показывает 100 записей с корректными полями; алерт срабатывает при
искусственно увеличенном inference.

**Acceptance Scenarios**:

1. **Given** сервис обслуживает трафик, **When** средняя inference latency
   за скользящие 5 минут превышает 30 секунд, **Then** публикуется алерт
   администратору.
2. **Given** сервис обслуживает трафик, **When** доля запросов с
   `insufficient_history` или `source_unavailable` за 15 минут превышает
   настроенный порог, **Then** публикуется алерт.

---

### User Story 5 — Классификация ликвидности тикеров (Priority: P3)

Отдельный сценарий: классификация тикеров по ликвидности / «голубая фишка».
Нужно довести побочный RandomForest из ноутбука до честной оценки — устранить
дисбаланс классов, получить приемлемый recall на редком классе.

**Why this priority**: вспомогательная фича для фильтрации универса тикеров
перед обучением прогнозной модели. P3 — не блокирует основные сценарии.

**Independent Test**: на выборке из `archive/D1` классификатор воспроизводимо
отделяет голубые фишки от остальных с recall ≥ заявленного порога на обоих
классах.

**Acceptance Scenarios**:

1. **Given** набор из 249 тикеров D1, **When** запущена классификация,
   **Then** recall по классу «голубая фишка» ≥ 0.80 и по классу
   «прочие» ≥ 0.90 на стратифицированном holdout’е.

---

### Edge Cases

- **Пустой/повреждённый CSV** в `archive/`: сервис отклоняет обучение с
  понятной ошибкой, не записывает битый артефакт.
- **Разрывы в истории** (нерабочие дни, длительные паузы торгов): модель
  строится на торговых барах, разрывы не заполняются искусственно.
- **Резкие гэпы** (корпоративные события, сплиты): результат помечается
  пониженной уверенностью; пользователь получает предупреждение в
  `factors[]`, что последний бар аномален.
- **Устаревшая модель**: если актуальная версия для тикера обучена более
  N дней назад (по умолчанию 14), сервис явно сигнализирует
  `model_stale = true` и предлагает админу переобучить.
- **Одновременные запросы на обучение одного тикера**: второй запрос
  отклоняется либо ставится в очередь — избегаем гонок за артефакт.
- **Горизонт/таймфрейм, не предусмотренные моделью**: отказ, а не молчаливая
  экстраполяция.
- **Запрос вне торговой сессии MOEX**: сервис отвечает, но помечает
  `outside_trading_hours = true`; свежесть данных — ответственность
  вызывающей стороны.
- **Устаревший OHLCV в Redis** (Data Collector отстал или упал):
  запрос отклоняется с кодом `stale_ohlcv`, указывается возраст
  последнего бара; сервис фиксирует событие в inference-журнале
  для наблюдаемости (FR-015).
- **Устаревший sentiment** (Sentiment Pipeline отстал): inference
  продолжается без sentiment, результат маркируется сниженной
  уверенностью; факт деградации источника идёт в `factors[]` и
  в inference-журнал.

## Requirements *(mandatory)*

### Functional Requirements

**Прогноз (inference)**

- **FR-001**: Сервис MUST принимать запрос на прогноз по gRPC
  с параметрами `ticker`, `timeframe`, `horizon` и возвращать ожидаемую
  траекторию, доверительные границы, вектор `factors[]`,
  `mape_at_generation`, `model_version`, `generated_at`. Контракт gRPC
  версионируется (префикс пакета, например `finzooka.ml.v1`).
- **FR-002**: Сервис MUST отказываться выдавать прогноз, если обученной
  версии модели для пары (ticker, timeframe) нет либо данных у тикера
  меньше минимального порога (500 баров).
- **FR-002a**: Для live inference сервис MUST читать свежие OHLCV и
  sentiment-агрегаты из общего Redis-кэша (поставщики — сервисы
  `Data Collector` и `Sentiment Pipeline` из C4). Архив `archive/`
  предназначен только для обучения и бэктеста и не используется для
  live-запросов.
- **FR-002b**: Свежесть входных данных MUST валидироваться перед
  inference:
  - OHLCV: возраст последнего бара ≤ 1× длительности запрошенного
    таймфрейма (для M15 ≤ 15 мин, для H1 ≤ 60 мин, для D1 ≤ 1 день);
    иначе запрос отклоняется с кодом `stale_ohlcv`.
  - Sentiment: возраст агрегата ≤ 60 мин; иначе сервис переходит
    в fallback-режим без sentiment и помечает сниженную уверенность
    в `factors[]` (FR-014).
  - Оба порога настраиваются через конфигурацию; дефолты указаны выше.
- **FR-003**: Сервис MUST выполнять прогноз минимум на двух независимых
  группах факторов: (а) OHLCV + технические индикаторы и (б) хотя бы один
  экзогенный фактор (sentiment или новостной фон). При отсутствии (б)
  MUST перейти в fallback и явно отметить сниженную уверенность
  (принцип III).
- **FR-004**: Сервис MUST формировать человекочитаемое объяснение прогноза
  (2–3 предложения) и перечень вкладов признаков для каждого сигнала
  (принцип I).
- **FR-005**: Сервис MUST завершать inference за ≤ 15 секунд (цель) и
  отклонять запросы с ожидаемым выполнением > 60 секунд (MVP acceptable).

**Обучение / валидация**

- **FR-006**: Сервис MUST уметь обучать модель по паре (ticker, timeframe)
  на основе CSV из каталога `archive/<timeframe>/<ticker>_<timeframe>.csv`.
- **FR-007**: Обучение MUST применять walk-forward валидацию минимум на
  5 фолдах; запрещено использовать данные из будущего при расчёте
  признаков (anti look-ahead).
- **FR-008**: Сервис MUST сохранять артефакт модели с уникальным
  `model_version` и метаданные: метрики per-fold и aggregate (MAPE, RMSE,
  MAE, R², directional accuracy), окно обучения, список использованных
  признаков, хеш входного датасета.
- **FR-009**: Сервис MUST формировать отчёт «old vs new» при каждом
  переобучении: разница метрик и рекомендация «продвигать / не продвигать».
- **FR-010**: Сервис MUST хранить минимум 3 предыдущие версии модели на
  тикер и позволять откат (целевое RTO < 30 мин).
- **FR-026**: Сервис MUST поддерживать состояние `shadow` для модели:
  для каждого входящего forecast-запроса параллельно с production-версией
  shadow-версии выполняют предсказание и записывают его в отдельный
  журнал вместе с фактом (когда факт становится известен). Shadow-модели
  NE выдаются внешним потребителям.
- **FR-027**: Сервис MUST предоставлять операцию `promote(model_version)`
  и `archive(model_version)`, вызываемые админом через admin-панель или
  CLI; промоушен переключает production-трафик атомарно (активная
  версия всегда ровно одна на пару (ticker, timeframe)).
- **FR-028**: Сервис MUST формировать shadow-отчёт по запросу админа
  с метриками за shadow-период (MAPE, RMSE, dir. accuracy, win rate)
  и дельтой относительно действующей production-версии.
- **FR-029**: Сервис MUST автоматически планировать переобучение всех
  production-моделей раз в неделю в окне обслуживания (воскресенье
  ночью, вне торговой сессии MOEX); расписание настраивается
  (cron-выражение). Ручной запуск переобучения через admin-панель /
  CLI MUST оставаться доступен поверх расписания в любое время.
- **FR-030**: Автоматически обученные по расписанию модели MUST
  проходить тот же workflow, что и ручные: walk-forward валидация →
  `shadow` при прохождении минимальных метрик → ручное подтверждение
  admin’ом перед переключением production-трафика (FR-026, FR-027).

**Бэктест**

- **FR-011**: Сервис MUST предоставлять бэктест произвольного периода
  (минимум 6 месяцев) с агрегатами MAPE / RMSE / win rate / directional
  accuracy и сравнением с двумя baseline’ами (`naive` + `ohlcv_only`).

**Данные**

- **FR-012**: Сервис MUST поддерживать все 9 таймфреймов из `archive/`
  (MN1, W1, D1, H4, H1, M30, M15, M10, M5); фактическое обучение на
  MVP MUST быть ограничено «голубыми фишками» (принцип VII); остальные
  тикеры остаются в каталоге для будущих релизов.
- **FR-013**: Сервис MUST валидировать входные CSV: корректный набор
  колонок (`datetime,open,high,low,close,volume`), монотонный временной
  индекс, отсутствие отрицательных цен/объёмов; при нарушениях — отказ
  с детальным сообщением.
- **FR-014**: Сервис MUST агрегировать источники экзогенных данных
  минимум из 2 (принцип III); sentiment-агрегаты читаются из общего
  Redis-кэша (владелец — отдельный сервис `Sentiment Pipeline` из C4);
  при отсутствии/устаревании ключей fallback MUST работать только на
  OHLCV-производных признаках с соответствующей пометкой в `factors[]`.

**Наблюдаемость и целостность**

- **FR-015**: Сервис MUST писать в журнал inference для каждого запроса:
  `ticker`, `timeframe`, `horizon`, `model_version`, latency, статус
  (`ok` / `degraded` / `reject`), `mape_at_generation`.
- **FR-016**: Сервис MUST публиковать метрики (MAPE, win rate, latency,
  доля отказов) в admin-панель ежедневно на уровне «per ticker × per
  timeframe» (принцип V).
- **FR-017**: Сервис MUST запускать health-check компонентов (train
  pipeline, inference, registry, feature store) не реже 1 раза в минуту
  и слать алерт администратору при сбое.

**Безопасность и соответствие**

- **FR-018**: Сервис MUST не хранить персональные данные пользователей —
  работает только с обезличенными рыночными данными (принцип VI).
- **FR-019**: Любой выходной текст (`explanation`), видимый пользователю,
  MUST формироваться без фраз, обещающих доход, и сопровождаться
  пометкой «не является инвестиционной рекомендацией» на стороне backend
  (сервис MUST гарантировать отсутствие слов-триггеров из чёрного списка).
- **FR-020**: Артефакты моделей MUST храниться локально на сервере
  (152-ФЗ, локализация данных в РФ); публикация в сторонние облака
  запрещена без отдельного решения.

**Минимальный набор улучшений по сравнению с ноутбуком**

- **FR-021**: Сервис MUST устранить look-ahead bias, присутствующий в
  текущей реализации (экзогенные признаки считаются по полной истории
  до split’а).
- **FR-022**: Сервис MUST публиковать сравнение с двумя baseline’ами при
  валидации и отвергать продвижение модели с R² < 0 относительно
  наивного baseline’а.
- **FR-023**: Гиперпараметры (окно, порядок AR, список признаков) MUST
  подбираться на поисковой сетке или байесовским оптимизатором, а не
  вручную.
- **FR-025**: Primary candidate — ARMAExo из ноутбука с доработками
  (FR-007, FR-021, FR-023). Если после всех доработок на тестовом
  наборе голубых фишек (SC-001) метрики не достигаются, сервис MUST
  допустить переключение на gradient-boosting-модель (LightGBM/XGBoost)
  в качестве production-моделью. Решение о переключении фиксируется в
  `Training Run` как отдельный event `family_switch` с обоснованием
  метриками. ARMAExo в любом сценарии остаётся доступен как один из
  baseline’ов в бэктесте (FR-011) наряду с `naive` и `ohlcv_only`.
- **FR-024**: Классификатор ликвидности (US-5) MUST применять стратегию
  борьбы с дисбалансом классов (стратифицированная выборка, взвешивание
  или oversampling) — текущий notebook даёт 0% recall по редкому классу.

### Key Entities *(include if feature involves data)*

- **Ticker** — торговый инструмент MOEX (строковый код, например `SBER`);
  имеет историю OHLCV в нескольких таймфреймах и индикатор «голубая фишка».
- **Timeframe** — одно из {MN1, W1, D1, H4, H1, M30, M15, M10, M5};
  определяет частоту наблюдений.
- **OHLCV Bar** — одна запись CSV: `datetime, open, high, low, close, volume`;
  минимальная единица истории.
- **Model Artifact** — сохранённая обученная модель для пары (ticker,
  timeframe); имеет `model_version`, метаданные обучения, метрики
  walk-forward, ссылку на датасет, состояние
  (`training` / `shadow` / `production` / `archived` / `do_not_promote`).
  На пару (ticker, timeframe) одновременно допустимо: ровно одна
  `production` + ноль или более `shadow` + сколько угодно `archived`.
- **Forecast** — ответ сервиса на запрос прогноза: траектория,
  доверительный интервал, `factors[]`, `explanation`, `mape_at_generation`,
  `model_version`, `generated_at`.
- **Factor Contribution** — запись в `factors[]`: имя признака
  (например, `rsi_14`, `sentiment_tpulse_mean`), числовой вклад, источник,
  флаг актуальности.
- **Backtest Report** — массив «прогноз vs факт» за период плюс
  агрегированные метрики.
- **Training Run** — запись журнала обучения: параметры, метрики
  per-fold, сравнение с предыдущей версией, решение «продвигать».
- **Inference Log Entry** — запись о каждом вызове прогноза: latency,
  статус, версия модели, деградации источников.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На тестовом наборе из минимум 5 голубых фишек MOEX
  (SBER, GAZP, LKOH, GMKN, ROSN) агрегированный MAPE на walk-forward
  валидации ≤ **5%** для таймфрейма M15 при горизонте 4 бара и
  ≤ **3%** для D1 при горизонте 1 бар.
- **SC-002**: Directional accuracy (доля корректно предсказанных
  направлений) ≥ **55%** на том же наборе — строго выше случайного
  50%-го baseline’а.
- **SC-003**: На holdout-периоде (последние 6 месяцев из `archive/`)
  win rate сигналов на основе прогноза ≥ **52%** при фиксированных
  правилах SL/TP.
- **SC-004**: Среднее время одного inference ≤ **15 секунд** в 95%
  запросов; p95 ≤ **30 секунд**; timeout 60 секунд (принцип V).
- **SC-005**: Обучение одного тикера × таймфрейма по историческому
  CSV из `archive/` завершается за ≤ **10 минут** на референс-железе
  (4 CPU / 12 ГБ ОЗУ, целевое окружение Finzooka).
- **SC-006**: Каждый ответ сервиса содержит поле `explanation` (непустая
  строка) и массив `factors[]` длиной ≥ **3**; проверяется на 100%
  запросов в наблюдаемости (принцип I).
- **SC-007**: Сервис обнаруживает и отклоняет повреждённые CSV
  со 100% покрытием предзаданного набора дефектных кейсов
  (пустой файл, пропуски, нарушение монотонности, отрицательная цена).
- **SC-008**: Время простоя inference вне MOEX-сессии (до 10:00 и после
  18:50 MSK) не учитывается в SLA; в рабочие часы доступность ≥ **95%**
  на MVP.
- **SC-009**: По результатам бэктеста регрессия относительно двух
  baseline’ов (`naive` и `ohlcv_only`) положительная: aggregate MAPE
  новой модели ниже обоих baseline’ов на ≥ **10%** относительных.
- **SC-010**: Классификатор ликвидности (US-5) даёт recall ≥ **0.80**
  по редкому классу «голубая фишка» на стратифицированном holdout’е —
  тем самым устраняется дефект текущего ноутбука (0% recall).

## Assumptions

- Данные `archive/` считаются статическим обучающим датасетом (снапшот
  из Kaggle, 1999-06 … 2024-08). Их обновление из T-Invest API — отдельная
  фича (`data-collector`), за пределами scope’а этого спека.
- Экзогенные источники (sentiment T-Pulse, новости) подключаются через
  внутренний API других сервисов Finzooka; наличие их контрактов —
  предусловие для FR-003 / FR-014. Если контрактов ещё нет, временный
  fallback (только OHLCV-производные признаки) удовлетворяет MVP.
- Минимальная длина истории для обучения — 500 баров на запрошенном
  таймфрейме (разумный дефолт для ARMA-подобных моделей).
- Максимальный поддерживаемый горизонт прогноза — 14 баров (как в
  ноутбуке); расширение — отдельный релиз.
- Референс-железо для перформанс-SLA: 4 CPU / 12 ГБ ОЗУ / GTX 1650
  (Technical Constraints конституции).
- Чёрный список слов-триггеров для `explanation` (FR-019) формируется
  и поддерживается отдельным конфиг-файлом; первичный список
  («гарантировано», «точно вырастет», «100%») входит в поставку.

## Out of Scope

- Автоматическая торговля и интеграция с брокерским API для выставления
  ордеров (принцип II Navigator, Not Autopilot).
- Сбор свежих рыночных данных из T-Invest API (это `data-collector`,
  отдельный модуль).
- Сбор sentiment из T-Pulse и новостных источников (это
  `sentiment-pipeline`, отдельный модуль).
- Telegram Bot и Mini App (отдельные модули, потребляют контракт
  этого сервиса).
- Персонализированные стратегии пользователя: сервис даёт прогноз и
  признаки, адаптация под стратегию — на уровне backend’а/оркестратора.
- Второй эшелон тикеров в MVP (принцип VII) — данные в архиве есть,
  обучение отложено до v2.0.

## Dependencies

- **archive/** — 249 CSV × 9 таймфреймов, входные исторические данные
  (обязательная зависимость).
- **Model Registry** (хранилище артефактов) — каталог на диске + индекс
  в основной БД; конкретный выбор на этапе плана.
- **Admin Panel** (US-4) — потребитель метрик; контракт публикации
  согласовать отдельно.
- **Sentiment Pipeline (отдельный сервис из C4)** — поставщик
  sentiment-агрегатов через общий Redis; контракт ключей
  согласовать при планировании. При отсутствии/устаревании ключей
  forecast-сервис переходит в fallback (FR-014).
